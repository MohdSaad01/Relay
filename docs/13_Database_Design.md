# Database Design

Version: 1.0

---

# 1. Purpose

This document is the authoritative reference for the Relay Version 1 database schema.

It defines every table, field, constraint, relationship, and the reasoning behind each decision. It was produced during the Database Design milestone and finalized before any SQLAlchemy models were written.

If future changes are made to the schema, this document should be updated alongside them.

---

# 2. Scope and Philosophy

Relay V1 uses SQLite (`03_Tech_Stack.md`, `08_Architecture_Decisions.md` ADR-005) and stores only metadata. Files themselves always remain on disk (`02_Architecture.md` §6-7).

The database describes a single desktop installation's view of the world: the phones it has paired with, the files it has chosen to share, and the transfers it has performed. There are no user accounts (Charter §5) and no concept of the desktop needing a row describing itself.

The schema favors a small number of explicit, well-understood tables over generic or speculative structures. Nothing is included to support a feature that has not been requested for Version 1.

---

# 3. Entity Overview

| Entity | Responsibility |
|---|---|
| `devices` | Identity and pairing record for a trusted Android device |
| `sessions` | Short-lived auth tokens issued to a paired device |
| `shared_files` | Metadata for files the desktop user has explicitly shared |
| `transfers` | One row per file transfer (in-progress or historical) |
| `app_settings` | Single-row table of user-editable runtime preferences |

Pairing tokens are **not** a table. See §9.

---

# 4. Table: `devices`

**Purpose:** Represents an Android device that has completed pairing and is trusted to call protected endpoints.

| Field | Type | Nullable | Default | Immutable after creation |
|---|---|---|---|---|
| `id` | Integer (PK) | No | autoincrement | Yes |
| `device_identifier` | String | No | — | Yes |
| `device_name` | String | No | name reported at pairing | No |
| `platform` | Enum(`android`) | No | — | Yes |
| `device_secret_hash` | String | No | — | Yes |
| `paired_at` | DateTime | No | now | Yes |
| `last_seen_at` | DateTime | Yes | NULL | No |
| `created_at` | DateTime | No | now | Yes |
| `updated_at` | DateTime | No | now | No |

**Constraints:** `UNIQUE(device_identifier)`.

**Indexes:** unique index on `device_identifier` (pairing lookup); index on `last_seen_at` (device-management UI sort).

**Relationships:**
- One-to-many → `sessions`, `ON DELETE CASCADE`.
- One-to-many → `transfers`, `ON DELETE SET NULL` (history survives device removal).

**Reasoning:**
- `device_identifier` is a UUID generated by the Android app itself on first install and presented during pairing. It is the stable external identity; the primary key stays a plain internal integer.
- `device_secret_hash` is a long-lived credential established at pairing time, used to mint new `sessions` rows after the app restarts without re-pairing. Only the hash is stored, never the plaintext secret.
- **Device removal is a hard delete** — approved for Version 1. Removing a device deletes its row outright rather than flagging it inactive. This is simpler than a soft-delete/status model and satisfies the requirement that session tokens be invalidated on removal for free, via `ON DELETE CASCADE` on `sessions`. Soft deletion may be reconsidered in a future version if a "recently removed devices" feature is ever needed.

# 5. Table: `sessions`

**Purpose:** A currently-valid session token for a paired device, obtained by presenting the device's secret. Satisfies `10_Security.md` §8: expires, is renewable, is invalidated on device removal.

| Field | Type | Nullable | Default | Immutable |
|---|---|---|---|---|
| `id` | Integer (PK) | No | autoincrement | Yes |
| `device_id` | Integer (FK → `devices.id`, `ON DELETE CASCADE`) | No | — | Yes |
| `token_hash` | String | No | — | Yes |
| `issued_at` | DateTime | No | now | Yes |
| `expires_at` | DateTime | No | now + configured lifetime | No (updated on renewal) |
| `last_used_at` | DateTime | Yes | NULL | No |

**Constraints:** `UNIQUE(token_hash)`.

**Indexes:** unique index on `token_hash` (checked on every authenticated request); index on `device_id`; index on `expires_at` (expiry cleanup).

**Reasoning:** Only the token hash is stored, so a copy of the database file cannot be replayed as a valid bearer token. There is no `revoked_at` flag — expired or superseded sessions are deleted outright (on renewal, or by periodic cleanup), so this table only ever holds currently-valid tokens.

# 6. Table: `shared_files`

**Purpose:** Metadata for files the desktop user has explicitly added to the shared list. Per `11_File_Transfer.md` §5, this is the only thing that grants a paired device visibility into a file — nothing outside this table is ever exposed.

| Field | Type | Nullable | Default | Immutable |
|---|---|---|---|---|
| `id` | Integer (PK) | No | autoincrement | Yes |
| `file_name` | String | No | filename at share time | Yes |
| `file_path` | String | No | — | Yes |
| `file_size` | Integer (bytes) | No | size at share time | Yes |
| `mime_type` | String | Yes | NULL | Yes |
| `shared_at` | DateTime | No | now | Yes |

**Constraints:** `UNIQUE(file_path)` — sharing the same path again updates/no-ops rather than creating a duplicate row, matching the "refresh the shared list" behavior in `11_File_Transfer.md` §6.

**Indexes:** unique index on `file_path`; optional index on `shared_at` for default list ordering.

**Relationships:** one-to-many → `transfers`, `ON DELETE SET NULL`.

**Reasoning:**
- `file_size` is captured at share time so the UI never has to recompute it from disk. It is a point-in-time snapshot, not a live value — if the underlying file changes size, the entry is refreshed by the existing "refresh shared list" flow, not by re-reading the file on every request.
- `mime_type` is nullable and captured at share time to simplify future UI rendering (icons, platform-specific handling) without requiring the client to infer it. It is optional because a type cannot always be determined from a file's extension or contents.
- No `checksum` field. Integrity verification is an explicit future enhancement (`11_File_Transfer.md` §16); adding the column now would carry no weight until a milestone actually uses it.

This table only represents files shared **from the desktop**. Android-initiated uploads do not get a `shared_files` row — the phone has no persistent backend of its own, so file selection for an upload is transient UI state, not a durable share. An upload produces only a `transfers` row with `shared_file_id = NULL`.

# 7. Table: `transfers`

**Purpose:** One row per individual file transfer. Serves both the in-progress view (progress reporting) and the "basic transfer history" required by the Charter, using a single table for both.

| Field | Type | Nullable | Default | Immutable |
|---|---|---|---|---|
| `id` | Integer (PK) | No | autoincrement | Yes |
| `device_id` | Integer (FK → `devices.id`, `ON DELETE SET NULL`) | Yes | — | Yes |
| `shared_file_id` | Integer (FK → `shared_files.id`, `ON DELETE SET NULL`) | Yes | — | Yes |
| `direction` | Enum(`send`, `receive`) | No | — | Yes |
| `file_name` | String | No | — | Yes |
| `file_size` | Integer (bytes) | No | — | Yes |
| `device_name` | String | No | — | Yes |
| `status` | Enum(`in_progress`, `completed`, `failed`, `cancelled`) | No | `in_progress` | No |
| `bytes_transferred` | Integer | No | 0 | No |
| `failure_reason` | String | Yes | NULL | No (set once, on failure) |
| `started_at` | DateTime | No | now | Yes |
| `completed_at` | DateTime | Yes | NULL | No |

**Constraints:** none beyond primary/foreign keys.

**Indexes:** `status` (active-transfers queries), `started_at` (history sort — the most common query), `device_id`.

**Reasoning:**
- `file_name`, `file_size`, and `device_name` are deliberately denormalized snapshots, copied in at transfer start rather than joined live from `shared_files` / `devices`. This is what makes the nullable, `SET NULL` foreign keys safe: if a shared file is later removed or a device is later deleted, transfer history still reads correctly instead of showing orphaned or blank rows. This is the standard pattern for audit/history tables.
- `direction` is framed from the desktop's perspective (`send` / `receive`) rather than `upload` / `download`, which is ambiguous depending on which device the term is spoken from.
- `completed_at` is a dedicated nullable timestamp, set once the transfer leaves `in_progress` (success, failure, or cancellation). It is intentionally separate from any generic "last updated" timestamp so that "when did this transfer finish" is always an explicit, unambiguous field rather than inferred from a mutation-tracking column.
- `failure_reason` (renamed from an earlier `error_message` working name) better reflects its purpose: it explains *why* a transfer did not complete, not a generic error log line.
- **`batch_id` has been removed for Version 1.** Sequential, one-file-at-a-time transfer processing (`11_File_Transfer.md` §10) does not require correlating multiple rows into a batch. If grouped/batch transfer semantics are introduced in a future version, a proper batch entity (e.g. a `transfer_batches` table with its own lifecycle) should be introduced at that time rather than reviving a loose correlation column.

# 8. Table: `app_settings`

**Purpose:** User-editable runtime preferences changed through the application UI. Distinct from static deployment configuration (`PORT`, `DATABASE_URL`, `LOG_LEVEL`), which remains in `.env` via the existing `app/core/config.py` and is not duplicated into the database.

| Field | Type | Nullable | Default | Immutable |
|---|---|---|---|---|
| `id` | Integer (PK) | No | always `1` | Yes |
| `device_display_name` | String | No | OS hostname at first run | No |
| `download_directory` | String | No | OS Downloads folder at first run | No |
| `discovery_enabled` | Boolean | No | `true` | No |
| `session_token_lifetime_minutes` | Integer | No | e.g. `1440` | No |
| `created_at` | DateTime | No | now | Yes |
| `updated_at` | DateTime | No | now | No |

**Relationships:** none — standalone singleton row.

**Reasoning:** A single explicit-column row was chosen over a generic key-value settings table. Version 1 has a small, fixed, known set of preferences; a key-value table would require per-type serialization and coercion for no real benefit at this scale. `session_token_lifetime_minutes` living here is what makes `sessions.expires_at` configurable, as required by `10_Security.md` §8.

# 9. Pairing Tokens: Not a Table

Temporary QR-pairing tokens (`10_Security.md` §6) are **not persisted to the database**. They are held in memory by the pairing service for the duration of the pairing attempt only.

**Decision:** confirmed during this milestone.

**Reasoning:**
- Pairing tokens are single-use and expire within minutes.
- The backend is embedded in, and runs as part of, the desktop application — there is no multi-process or restart-survival scenario where a pending pairing attempt should outlive the process. If the application restarts mid-pairing, the user simply starts the pairing flow again.
- Keeping short-lived security material out of persistent storage is a reasonable default — there is nothing to clean up and nothing to leak from a database file copy or backup.
- Avoids an extra table plus expiry-sweep logic for something that provides no durability benefit.

This will be implemented as an in-memory structure (e.g. a dictionary keyed by token, with TTL) inside the pairing service during the Pairing milestone.

# 10. Relationship Summary

```
devices (1) ──< sessions (many)              ON DELETE CASCADE
devices (1) ──< transfers (many)             ON DELETE SET NULL, name snapshotted
shared_files (1) ──< transfers (many)        ON DELETE SET NULL, name/size snapshotted
app_settings                                  standalone singleton
```

No table is deleted as a matter of routine operation except `devices` (explicit user action) and `sessions` (expiry cleanup). `shared_files` rows are removed when the user un-shares a file. `transfers` rows are never deleted by normal operation — they are the history.

# 11. Version 1 Tables

Required: `devices`, `sessions`, `shared_files`, `transfers`, `app_settings`.

# 12. Postponed / Explicitly Excluded

| Table / field | Why postponed |
|---|---|
| `pairing_tokens` | Kept in memory only — see §9 |
| `transfer_batches` | `transfers` processes sequentially in V1; a real batch entity can be introduced later if needed |
| `checksum` on `shared_files` / `transfers` | Integrity verification is a documented future enhancement |
| `devices.status` (soft delete) | Hard delete approved for V1; may be reconsidered later |
| Audit/security log table | Security events belong in the existing file-based logger (`LOG_DIR`), not the database |
| `users` / accounts | Explicitly out of scope (Charter §5) |
| Folder-sync tables | Explicitly out of scope (Charter §5, `11_File_Transfer.md` §3) |

# 13. Implementation Notes for the Database Milestone

These are implementation-level details that follow from this design and must be respected when the SQLAlchemy models and session setup are built:

* **SQLite foreign key enforcement must be explicitly enabled.** SQLite does not enforce `FOREIGN KEY` / `ON DELETE` behavior by default — `PRAGMA foreign_keys = ON` must be set on every connection (typically via a SQLAlchemy engine `connect` event listener in `app/database/session.py`). Without this, the `CASCADE` and `SET NULL` behaviors this schema relies on will silently not happen.
* Secrets and tokens (`devices.device_secret_hash`, `sessions.token_hash`) are stored hashed; the plaintext value is only ever held transiently and returned to the client once.
* `shared_files.file_size` and `transfers.file_size` are point-in-time snapshots in bytes, not live-computed values.

---

# 14. Why This Design Fits Version 1

The schema maps directly onto the Charter's stated V1 scope — pairing, device management, a shared list, transfers, basic history, preferences — with nothing speculative added. Five tables, no generic or key-value patterns, no unused enum values.

**Future expansion:**
- All tables use plain integer primary keys and standard foreign key relationships, so a future PostgreSQL migration (`08_Architecture_Decisions.md` ADR-005, `03_Tech_Stack.md` §19) is a data-copy exercise, not a redesign.
- `platform` on `devices` is already a string/enum rather than an implicit "always Android," so future iOS/macOS/Linux clients add new values, not new columns.
- `shared_files` and `transfers` are already decoupled via nullable foreign keys, so adding folder sync or checksum verification later is additive.

**Main trade-off:** favoring denormalized snapshot columns (`transfers.file_name`, `transfers.file_size`, `transfers.device_name`) over strict normalization. For a history/audit table this is the correct and standard pattern — it trades a small amount of duplicated data for history that remains readable after the things it references are deleted, which this domain explicitly requires.
